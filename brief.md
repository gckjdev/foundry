## Plan

## Auto PR review (Option A: same job, post-PR `pr_review` stage)

1. **State machine + policy + contract (shared)**
   - `packages/shared/src/states.ts`: add `pr_review` status/runner stage; legal edges `pr_ci→pr_review`, `pr_review→{implementing,pr_ci,queued,waiting_on_you,failed,cancelled}`; keep `nextRunnerStage(verifying) = pr_ci`; title "PR review".
   - `packages/shared/src/policy.ts`: add opt-in `auto_pr_review` (default false); reuse `max_review_loops` as the auto-fix loop budget.
   - `packages/shared/src/api.ts`: add `CiFailure`, `PrReviewContext` on `ClaimedJob`, and `PrReviewRequest`/response schemas.
   - `packages/shared/src/comments.ts`: render the GitHub review body from a report.
2. **DB**: `pr_review_sha` + `pr_review_count` columns on `jobs`, schema + migration `0010_pr_review.sql`.
3. **GitHub client**: `checkFailures(ref, sha)` (failed check runs + annotations + failed commit statuses) and `createReview(...)` (inline comments with a body-only fallback); implement in `octokit.ts` and `FakeGitHub`, with mock tests.
4. **Control plane**
   - `pr-review.ts`: `maybeStartPrReview` (once per head SHA when CI is no longer pending), `prReviewContext`, `submitPrReview` (post COMMENT review + record review evidence; approve→`pr_ci`+gate, blocking→requeue `implementing` with findings as input, budget spent→`waiting_on_you`).
   - `evaluateJobGate`: trigger the review before gating; `claimJob` attaches the PR/CI context; `runner-api` + web route add `pr-review`.
   - Panel/status map + board lane + GitHub project status.
5. **Runner**: claim at `pr_review`, skip recipe install/services, run a fresh read-only reviewer on a detached worktree at the PR head with the failed CI checks in the prompt, report through the new `submitPrReview` control call; cleanup.
6. **Tests**: control unit (trigger → claim → blocking fix loop / approval), runner unit (detached review + submit), Octokit mock (check failures + review fallback), e2e if practical.
7. **Docs**: `docs/api.md`/zh (runner action, claim payload, webhook behaviour) and `.foundry` policy docs for `auto_pr_review`.

## Questions and answers

- Q: How should the Auto PR review be wired into Foundry's job lifecycle? Context from the code: an independent reviewer already runs *before* the PR in the `reviewing` stage, and `check_run`/`check_suite`/`status` webhooks already re-evaluate the gate while a job sits in `pr_ci`. All options below trigger on the first completed CI result for the PR head, let the agent read the failing check details, and submit a GitHub review (REQUEST_CHANGES/COMMENT, inline comments when file+line resolve). They differ in how the work is scheduled and how fixes loop back.

Option A (recommended) — Same job, new post-PR stage: add a `pr_review` runner stage. When CI for the PR head completes (success or failure), the control plane re-queues the same job at `pr_review` once per head SHA. A fresh read-only agent reviews the pushed branch + failed check output, then Foundry submits one GitHub review. Blocking findings send the job straight back to `implementing` automatically (reusing the review loop budget, then handing to a human); a clean pass returns to `pr_ci`/gate. Smallest change that meets all four acceptance criteria; keeps the pre-PR reviewer.

Option B — Separate linked review job: spawn a child `pr_review` job per PR/CI completion, with its own kind, budget and timeline, runnable on any ready runner. It posts the GitHub review; if blocking, the existing changes-requested path reopens the parent job at `implementing`. Better isolation and parallelism, but adds a job kind, DB migration, scheduler/panel/metrics work and two jobs per PR.

Option C — Reuse the existing `reviewing` stage post-PR: no new stage; when CI completes, re-trigger the existing `reviewing` stage from `pr_ci`, extending it with PR/CI context and GitHub review submission. Smallest state-machine change, but one stage means two different things (pre-PR gate review and post-PR review) and needs a second-pass flag to avoid being skipped as already cleared.
  A: A — Same job, new post-PR `pr_review` stage (recommended)
