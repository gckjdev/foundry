# Handoff brief: Fix bug: board/inbox/runner keep refreshing while restarting the control plane/runner/webhook

Stage reached: **reviewing** · harness: claude-code · updated 2026-11-11T07:29:21.672Z

## Plan

Root cause: `LiveRefresh` renders once in the panel layout and subscribes the current page to tables chosen by `tablesForPage(pathname)`. The job-detail page is mapped to `["jobs", "questions", "events"]`, and the realtime service broadcasts an `events` INSERT for every agent tool call / usage flush, for every job in the team. So any open job page re-runs its whole server render (`jobDetail`, GitHub sync calls, new signed artifact URLs) every second or two while *any* job runs — matching the pasted log, where `GET /api/jobs/115fcd18/events?after=6705` never advances (that job has no new events) yet `GET /jobs/115fcd18` repeats and every artifact is re-fetched.

The job page already follows its live log by polling `/api/jobs/:id/events` from `LiveLog` every 2 s, so the realtime `events` subscription is redundant there. The server-rendered pieces that matter (status, plan, confidence, gate, timeline stage changes, questions) all come from `jobs`/`questions` writes.

Plan (smallest change):
1. `apps/web/src/components/realtime-tables.ts`: drop `events` from the `/jobs/` page's watched tables (`["jobs", "questions"]`) and document that the live log polls events itself; the broadcast is team-wide and per tool call.
2. `apps/web/src/components/realtime-tables.test.ts`: replace the "job page follows live events" assertion with one that event inserts do **not** re-render the job page, and keep/add assertions that job and question changes still do.
3. Verify: targeted `vitest run apps/web/src/components/realtime-tables.test.ts`, `biome check` on touched files, `pnpm --filter @foundry/web typecheck`, then the full recipe via `run_checks`.

## Findings

The log proves the events are other jobs' rows — `/api/jobs/115fcd18/events?after=6705` never advances while the page re-fetches every few seconds and re-signs all artifact URLs. Board/inbox/runners were already narrowed to their own tables and noise columns by the previous fix (20240b9).

The realtime `events` subscription stays removed, so no team-wide per-tool-call re-renders. Code quality — correct. The diagnosis matches the pasted log: the job page was the last page watching the `events` table, which gets an INSERT per tool call for every job on the team, so an unrelated running job re-rendered the whole page (which is why `after=6705` never moved yet `GET /jobs/:id` and every artifact re-sign repeated). Removing `events` from `/jobs/` in `tablesForPage` closes that; board/inbox/runners already excluded it, and the new tests lock the filter in. The lost server-rendered updates are covered by `needsServerRefresh`: I enumerated every kind against what the page renders outside the log and the set is complete — Timeline kinds (`stage_changed`, `resumed`, `question`, `answer`, `checkpoint`, `gate`, `error`, human `message`) plus `evidence` for the Evidence card (only `runnerEvidence` writes evidence rows, and it always emits the event). Agent/system messages are correctly log-only: `describe()` returns null for them, and `prs.ts` writes `jobs.prUrl` alongside the system message so the PR link still refreshes via `jobs`. No change weakens the LiveLog's own job-scoped polling; the cursor is a ref, so refreshes don't reset it or duplicate lines. Tests fail before the change (`["jobs","questions","events"]`) and pass after, and `needsServerRefresh` has per-kind plus empty-batch coverage. Scope is tight, no debug leftovers. I did not run the suite (no `node_modules` in this review checkout); I verified the logic by reading.

UI design — no visual/style/token changes, so design-system, layout, a11y and responsive checks do not apply. The user-facing behavior change (fewer whole-page re-renders, live log still self-scrolling) is preserved; `router.refresh()` from the poll keeps client state, so the composer/answer forms are unaffected. One display trade-off noted below. The attached screenshot only shows the live log rendering; a static image can't demonstrate the absence of refreshes, so I relied on the code and unit tests for that.

Security — no auth, input, output, secret or dependency changes; nothing to assess beyond confirming the poll endpoint still scopes by `team.id` via `eventsSince`, unchanged.

Non-blocking: the job header's live cost now lags (details in the finding).
- reviewing: Reviewer approved. The change suppresses the team-wide per-tool-call re-render while keeping job-scoped evidence/timeline updates flowing through the live-log poll. Running the recipe checks now.
